# Windows CPU 翻訳の検証（2026-11-23）

llama.cpp を公式 `master` の `8d60873dfb8619f2b5ed31adfbab07cccb40db5c` に更新した。`plamo3translate-tune` の `e300919cc` 向けパッチ5本を、Windows x64 の単一実行ファイルとアプリのデコーダーに合わせて移植した。[上流コミット](https://github.com/ggml-org/llama.cpp/commit/8d60873dfb8619f2b5ed31adfbab07cccb40db5c)

## 実測条件

Core i9-13900（8 Pコア・16 Eコア、32論理CPU）、Windows 11 Pro build 26300、clang-cl 24.0.0git、x64 Release、推論8スレッド。同じ配布用 PLaMo 3 Translate 0.8B Q4_K_M（SHA-256 `70891ec70dc7ab4205745a38307867c2881b99239f20327927633abfe4bc9ec6`）を使用した。

旧版はアプリ `9d73c52` と llama.cpp `a4d4f2fd4`。上流更新のみの版は同じアプリの既存 Windows AVX2 カーネルを保って llama.cpp を更新した。適用版には今回の最適化も含む。各 PDF を各版で5回ずつ、計45ページ翻訳した。実行順を入れ替え、1回ごとに新しいプロセスでモデルを開いた。OS のファイルキャッシュはウォーム。原文は毎回 PDFium で抽出し、通常の日本語訳を生成した。

## 速度と訳文

各欄は5回の中央値（秒）。短縮率は上流更新のみの版からの変化。

| PDF | 入力トークン | 旧版の翻訳 | 上流更新のみの翻訳 | 適用版の翻訳 | 翻訳時間の短縮率 | プロセス時間（旧版 / 上流のみ / 適用版） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| P01 | 58 | 0.696 | 0.697 | 0.607 | 13.0% | 2.38 / 2.05 / 2.23 |
| 科学文の要旨 | 119 | 1.955 | 1.983 | 1.685 | 15.0% | 3.72 / 3.33 / 3.24 |
| 長いライセンス文 | 582 | 8.811 | 9.032 | 6.619 | 26.7% | 10.41 / 10.39 / 8.25 |

翻訳時間はプローブが報告するプロンプト評価と生成の合計。プロセス時間には起動、PDF・モデルの読込、終了を含む。P01 は短い3段落、要旨は108語の科学文、長文はリポジトリの MIT・Chromium BSD ライセンスから生成した1ページで、512トークンの入力バッチをまたぐ。CPU負荷やモデルの読込時間は試行ごとに変動する。

適用版の翻訳時間の範囲は P01 が0.54～0.84秒、要旨が1.56～1.83秒、長文が6.42～8.06秒だった。モデルを毎回開く条件では、P01 のプロセス時間は上流のみの版より0.18秒長かった。

同一構成・同一 PDF の5回の訳文 SHA-256 はすべて一致した。上流のみの版と適用版では要旨の訳文が全文一致し、P01 は「再入力」を囲む括弧の有無、長文は表現や語順に違いが出た。適用版の出力トークン数は順に42・124・485。P01 と長文では近似出力層を無効にしても、適用版の既定設定と同じ訳文が得られた。この試験は訳文の再現性を確認したもので、翻訳品質の優劣は評価していない。

## Windows と macOS のソース分離後の再検証

同じ Windows 機とモデルで、上流更新のみの版と分離後の Windows Release を各5回比較した。数値はモデル読込を除く翻訳時間の中央値。

| PDF | 上流更新のみ | Windows パッチ適用 | 変化 |
| --- | ---: | ---: | ---: |
| P01 | 0.661 秒 | 0.868 秒 | 31.3% 増 |
| 科学文の要旨 | 1.822 秒 | 1.502 秒 | 17.6% 減 |
| 長いライセンス文 | 8.223 秒 | 5.840 秒 | 29.0% 減 |

短文の P01 は試行間の変動が大きかった。追加で上流更新のみ・分離前の適用版・分離後の適用版の全6通りの実行順を2巡し、各版12回測定した。中央値は順に 0.611 秒、0.509 秒、0.495 秒。短文では測定によって速さの順序が変わった。3種類の PDF とも分離後の訳文は全試行で分離前の適用版と一致した。Windows Release の CTest は、ターゲットを交互に準備する回帰テストを含めて34件すべて通過した。

macOS arm64 向けは Windows 上で Apple フレームワーク名を指定して CMake のビルド構成を検査した。未変更の公式ソースから標準 `ggml-metal` の実装8ファイルと埋め込みシェーダー36個が選ばれ、推論プローブのリンク先に Metal が入った。Windows 専用ソースは0件で、パッチ適用版を公式ソースとして指定すると構成時に停止した。このリビジョンでの Mac 実機ビルドと Metal による翻訳は未検証。

## 取り込んだ処理

- AVX-VNNI 対応 CPU で Q4_K・Q6_K の 8×4 再配置カーネルを使う。CPUID と OS のベクトルレジスタ対応を調べ、従来の AVX2・汎用経路も同じ実行ファイルに収めた。命令セットの指定は個別のソースに限った。
- F16 の KV キャッシュを使う16ヘッド・次元128の MQA で AVX2 FlashAttention を使う。対応する寸法、データ型、ストライド、マスク、ワーク領域を確認する。
- 小さい演算を1ワーカーでまとめて実行する。Windows のハイブリッド CPU では、プロセスに許された CPU の範囲で物理 P コアを先に割り当てる。トポロジーとデコード上限はスレッドプールごとに決める。
- 同梱モデルの Q6_K 出力層では、1ビットの索引で候補を絞り、候補のスコアを Q6_K で再計算する。索引に約21 MiBを使い、モデルと一緒に解放する。各推論の作業領域に探索用の表を置く。開発時は `GGML_NO_FAST_LMHEAD=1` で全語彙の Q6_K 計算と比較できる。
- アプリが表示不能な制御トークンを除外した後に AVX2 で最大スコアを探す。同点なら先頭のトークンを選ぶ。llama.cpp の CLI 用サンプラーはアプリにリンクしない。

## 安定性

- Release の CTest 33件がすべて合格。製品 EXE でも P01 を開き、翻訳ペインの全文がプローブの結果と一致し、正常終了した。起動ディレクトリのファイル一覧・サイズ・更新時刻に変化はなかった。
- 実モデルで公式トークン列14件、通常・やさしい日本語、複数バッチの入力、ストリーミング中のキャンセル、出力上限後の次の翻訳、モデル解放後の再読込を検証した。再読込後も同じ入力の訳文が一致した。推論中の GGUF への書き込みは Windows が拒否し、モデルを閉じた後は試験用コピーへの書き込みが可能になった。
- 同じ EXE で AVX2・汎用経路（`OPT_CPU_KERNELS=avx2` / `portable`）、1・32スレッド設定、Pコア固定の無効化、全語彙評価でもページが完了した。32スレッド設定時の単一トークン生成は P コアの論理スレッド数までに制限する。
- 静的 CRT、命令セット別オブジェクトの外部関数の重複、最終 EXE の DLL 依存・CFG・CET の検査を通過した。Westmere 命令シミュレーターは起動時にプローブのスレッドを取得できず、命令トレースは未確認。旧 CPU の実機および macOS の CPU・Metal も未検証。

## 再現と上流更新

各構成の `translation_probe.exe` を別名で用意し、開発用シェルで実行する。スクリプトは試験用 PDF を一時ディレクトリに作り、各回の時間・トークン数・訳文 SHA-256 と中央値を標準出力へ出す。

```powershell
python scripts/benchmark_translation.py --model .work/release-model/plamo-3-translate-0.8b-Q4_K_M.gguf --threads 8 --runs 5 old.exe upstream.exe tuned.exe
ctest --preset windows-x64-release --output-on-failure
build/windows-x64-release/inference_probe.exe .work/release-model/plamo-3-translate-0.8b-Q4_K_M.gguf cpu tests/fixtures/plamo3-pfml3-reference.tsv
```

次回上流更新時は、公式コミットを取得し、別の作業ツリーで `deps/patches/windows-x64/plamo3-cpu.patch` を `git apply --3way --index` して差分を確認する。上流で取り込まれた実装は該当する差分を削る。レビュー済みの index から `git diff --cached --binary <上流コミット>` でパッチを更新し、`git write-tree` の値と上流コミットを依存 lock に記録する。bootstrap は Windows 用の作業ツリー `.work/src/windows-x64/llama.cpp` でビルド用コミットを再現する。macOS は `.work/src/llama.cpp` の公式コミットと標準 Metal を使う。更新後はライセンス通知を再生成し、上記の比較、CTest、実モデル・実行ファイルの検査を繰り返す。
