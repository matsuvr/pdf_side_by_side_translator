# Windows PDF解析プロセスの分離

## 境界

Windowsの製品GUIではPDFiumを直接呼び出さず、PDF処理サービスの
IPCクライアントを所有する。同じ実行ファイルの内部ワーカーモードを
文書単位で起動するため、従来の単一EXE配布を維持する。ワーカー入口は
wxWidgetsやアプリ本体を初期化する前に分岐する。macOSの経路は従来どおり。

- 親プロセスが利用者の選択したファイルを読み取り専用で開き、開いた
  ファイルオブジェクトの読み取りハンドルを継承する。子にはPDFのパスを
  送信しない。Windowsが通常のファイルとして読み取れるUNC・共有ドライブ
  等も対象とする。4 GiB超のファイルについては、同じファイルオブジェクトの
  読み取り専用マッピングを使う。
- 制限付きトークン（追加権限を削除し、低い整合性レベルを設定）で起動し、
  ジョブオブジェクトでコミットメモリを1 GiB、同時プロセス数を1に制限する。
  クリップボードやシステム設定などのUI操作も制限する。環境変数はOSの
  ルートディレクトリに限定し、個人環境の変数を継承しない。
- 子が継承するハンドルのリストを限定する。匿名パイプで要求と結果を
  受け渡し、パスワードはコマンドラインに載せず、送受信バッファを使用後に
  消去する。実行時ファイル・一時ファイルを新設しない。
- IPCには明示的な整数、有限の数値、UTF-8文字列を使用する。親側で
  長さ（最大48 MiBのフレーム、32 MiBの復元メモリ予算）、列挙値、ページ識別子、
  文字のUTF-8境界と元文字範囲、タイル座標、画像サイズ・strideを検査する。
  子からポインタやファイル名を受け取って利用することはない。
- 開く処理は60秒で打ち切り、文書の切り替え・閉じる操作・終了で子を停止
  する。子が異常終了した場合は本体がエラーを表示し、別のPDFを開ける。
  起動時にトークン・ジョブ・動的コード禁止を成立させられない場合も、
  PDFの読込エラーとする。本体内解析には戻さない。

PDF描画、ページ情報、原文抽出、検索、OCRへ渡すページ画像は、既存の
PDF処理サービスを子の中で利用する。すでに受領して検証済みのレイアウトに
対する文字列検索は親で行い、重複するPDF解析を避ける。

## 保護できる範囲

初期段階のプロセス分離・書き込み制限である。PDFiumの異常終了を本体から
隔離し、通常権限を持つ本体や他プロセスへの書き込み・子プロセス増殖などの
影響を抑える。低整合性のトークンは同一ユーザーが読めるファイルへの読み取り
アクセスやネットワークアクセスをすべて禁止する仕組みではない。
機密データを完全に隔離するサンドボックスとは区別する。
AppContainer等による読み取り・通信も含めた制限は、単一EXE配布、一般の
展開先のACL、フォント利用およびファイル共有対応との両立を実機で検証する
次の課題とする。

## 受け入れ検証（Windows実機）

従来のCTestに加え、次の各テストを実行する。

- `bounded_pdf_worker_protocol`：フレーム切断、過大な長さ、異常な列挙値、
  不正UTF-8、元文字範囲、画像サイズの拒否。
- `pdf_async_wire_roundtrip`：PDFiumによる実際の描画、文字抽出、
  回転、検索、文書切り替えをIPCのエンコード／デコードに通す。
- `restricted_pdf_parser_process`：同一入口の子を実際に起動し、
  別のPID・ジョブ所属・低整合性を検査。描画、抽出、検索、OCR用画像、
  パスワードの再入力、子の異常終了後の再オープン、終了を確認。

最終配布ZIPでも、日本語フォント、4 GiB超のPDF、長いパス・共有ドライブ、
画面表示と翻訳の連携、再起動時にファイルを残さないこと、CPUとメモリを
確認する。既存のPDF処理・原文表示・翻訳テストも従来どおり実行する。
テスト入口が通過しても、実際に署名して配布するバイナリの動作確認が必要。

この設計はセキュリティ境界の強化に関するものであり、特定製品の検出結果や
誤判定の変化を根拠としたものではない。
