# セッションデータと安全性

この仕様は、安全性監査の [#1–#10](https://github.com/matsuvr/pdf_side_by_side_translator/issues/11) と追加検査の [#14–#17](implementation-status.md#privacy-and-responsiveness-follow-up) に対応する変更です。
以前の永続保存・キャッシュ復元の仕様を置き換えます。

## 自動でファイルを作らない

文書から抽出した原文、訳文、試行履歴、読書位置、ファイルのfingerprint、モデル選択と設定は、起動中のメモリ内だけに保持します。
SQLiteの状態DB・キャッシュDBは最初から `:memory:` で開き、`temp_store=MEMORY`、`journal_mode=MEMORY` を指定します。
状態ディレクトリ、キャッシュディレクトリ、lock、WAL/SHM、診断ログ、一時ファイルを作成しません。
本文は選択・コピーできる読み取り専用の表示です。原文・訳文の編集、原文の手入力、強制再翻訳、書き出しは提供しません。
`--data-dir` は廃止しました。起動引数はPDFのパスだけです。

終了時にディスク上のキャッシュを消す処理には依存しません。
通常終了・クラッシュ・強制終了のいずれでも、アプリが自動保存した文書キャッシュが残る経路を作らない設計です。
診断情報は、文書本文やパスを含まない固定項目の直近64件をGUIのメモリ内で保持します。

この範囲はアプリが管理するファイルです。OSの仮想メモリ、OSやドライバーが管理する情報、クラッシュダンプ、利用者がコピーしたクリップボードは別の管理対象です。
SSDの物理消去やOSによる記録の消去を保証する仕様ではありません。

## ファイル出力を行わない

訳文・原文・設定・読書位置・セッション状態の保存や書き出しはありません。
出力先ダイアログ、SQLiteのバックアップ、書き出し用の一時ファイル作成処理もありません。
入力PDF/GGUFを読み取り専用で開き、ディスク上のスナップショットや作業用コピーを作りません。
開発時のビルド生成物・テストfixtureは、製品実行時のこの方針とは別に扱います。

## 同梱モデルの読込

起動時は `plamo-3-translate-0.8b-Q4_K_M.gguf` を、Windowsでは `.exe` と同じ階層、Macでは `.app` の外側の同じ階層から読み込みます。
作業ディレクトリや過去の設定には依存しません。同梱GGUFがない場合だけファイル選択画面を開きます。
選択をキャンセルしてもPDFを閲覧でき、後から「モデル設定」で選択できます。
同梱ファイルがあって読込に失敗した場合は、通常のモデル読込エラーを表示します。
手動選択したパスも起動中だけ保持し、次回は再び同梱GGUFを確認します。

モデルの重みはアプリが所有するメモリへ読み込みます。変更可能なGGUFをmmapしたまま推論する経路は使わず、ディスク上のコピーも作りません。
生成中も既存の差分配信間隔でファイルの変更を確認し、変更を検出した場合は部分訳を保持して停止します。
モデルの初回読込は従来より時間がかかる場合があります。

## メモリの管理

| 対象 | 方針 |
| --- | --- |
| 翻訳キャッシュ | 既定256 MiB。SQLiteの固定schema分を除いたページ割当を含み、使用中文書も同じ上限の対象 |
| ページの翻訳状態 | 同じページ・モデル・profileの旧試行と不要な完成本文を置き換える。完成本文の二重保存を廃止 |
| 単一の大きすぎるキャッシュ項目 | 保存しない。GUIにある現在の結果は表示・コピー可能 |
| I/Oの作業キュー | ジョブは64件まで。翻訳状態の更新はページ・翻訳条件ごとにまとめる |
| GUI layout | 合計32 MiB。単一の巨大layoutも上限の例外にしない |
| layout生成 | 作業・出力を増やす前に予算を確認。既定の作業予算128 MiB、出力予算32 MiB。途中キャンセル可能 |
| 本文検索 | 本文全体を複製せず、前方・後方とも本文長と検索語長に対して線形時間で探索。検索語に比例する補助配列は検索後に破棄。前処理・本文走査とも途中キャンセル可能 |
| PDFium画像キャッシュ | 描画に `FPDF_RENDER_LIMITEDIMAGECACHE` を指定。固定版ではページ単位100 MiB。直近2ページを保持し、描画・抽出中のページは完了まで参照する |
| 描画・フォント | 表示は各辺262,144物理ピクセルまで。512ピクセルのタイルに分割する。隣り合う文字のフォントを比較するためにフォント名を取得・複製しない |
| 訳文の配信 | 1トークンの表現は4 KiB、1回の生成結果は1 MiBまで。GUIへの待ち行列は64件、生成した本文の合計4 MiBまで |
| UTF-8検証 | 全文の文字配列を作らず走査し、末尾まで検証。準備処理では途中キャンセルを確認 |
| 翻訳のトークン化 | モデルのcontext容量とvocabularyから導ける範囲で事前判定し、巨大な出力配列への再確保を避ける |
| 推論context | モデルの学習時最大を使用する。KV/computeの確保に失敗した場合だけ半分ずつ縮小し、実際の容量を診断へ表示する |

これらは各キャッシュ・処理段階の予算であり、アプリ全体のRSS上限ではありません。
モデル本体、PDFiumが解析するページや単一画像のデコード、OS/GUIの割当などは別にメモリを使います。
layoutの作業予算は各コンテナの増加を保守的に計上し、最終layoutの実容量も検査します。
非常に複雑なページで自動抽出を中止した場合も、PDFの表示を利用できます。

キャッシュから外れた完成訳は再表示時に再生成します。
## 読込中PDFの変更

PDFiumの通常の読み込みは、開いたファイルのハンドルに対する位置指定readを使います。
各readで範囲・ファイル識別情報・サイズ・更新時刻を確認し、Cコールバックを例外が越えないようにします。
POSIXの切り詰め可能なファイルをそのままmmapしてPDFiumへ渡す経路を廃止し、ディスクへのスナップショットも作りません。

Windowsの `FPDF_FILEACCESS` はオフセットが32 bitのため、4 GiB以上のPDFだけは既存の64 bit読込とread-only mappingを使います。
Windowsでは、PDF・GGUFの初回open、mapping、複製、モデルのストリームに一貫して読み取りだけを共有します。読み取り中に書き込み・切り詰め・パスの置換を試みると、競合する操作は失敗します。
通常サイズのWindows PDFとmacOS PDFはreadコールバックを使います。
Windowsの回帰試験ではスパースPDFの4 GiBを超える位置に相互参照表を置き、通常のPDFと同じ原文を抽出できることを確認します。

POSIXでは開いた実体の識別子・サイズ・更新時刻を照合します。同じサイズの上書きと時刻の復元を含む、すべての変更を検出できるわけではありません。

PDFとGGUFは、開いた実体が通常ファイルであることを確認します。
POSIXでは非ブロッキングで開いてから検査するため、書き手のいないFIFOを選んでも読込担当が待ち続けません。
通常ファイルへのシンボリックリンクは利用できます。

## 旧版のデータ

旧版の状態・キャッシュ・設定を読み込みません。schema移行、復元用バックアップ、削除も行いません。
ユーザーデータ領域を探索・作成・変更する処理はありません。

旧版の記録を手動で取り除く場合は旧版を終了し、Windowsは `%LOCALAPPDATA%\Offline PDF Translator`、Macは `~/Library/Application Support/Offline PDF Translator` を確認してください。旧版の `--data-dir` を使用した場合は指定先です。`state.sqlite3`、`Cache/cache.sqlite3`、`logs` など旧版のファイルを確認してから削除してください。
