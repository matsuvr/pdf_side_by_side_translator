# セッションデータと安全性

この仕様は、安全性監査の [#1–#10](https://github.com/matsuvr/pdf_side_by_side_translator/issues/11) に対応する変更です。
以前の永続保存・キャッシュ復元の仕様を置き換えます。

## 自動でファイルを作らない

文書から抽出した原文、手編集した原文、訳文、試行履歴、読書位置、ファイルのfingerprint、モデル選択と設定は、起動中のメモリ内だけに保持します。
SQLiteの状態DB・キャッシュDBは最初から `:memory:` で開き、`temp_store=MEMORY`、`journal_mode=MEMORY` を指定します。
状態ディレクトリ、キャッシュディレクトリ、lock、WAL/SHM、診断ログを自動作成しません。
`--data-dir` は廃止しました。起動引数はPDFのパスだけです。

終了時にディスク上のキャッシュを消す処理には依存しません。
通常終了・クラッシュ・強制終了のいずれでも、アプリが自動保存した文書キャッシュが残る経路を作らない設計です。
診断情報は、文書本文やパスを含まない固定項目の直近64件をGUIのメモリ内で保持します。

この範囲はアプリが管理するファイルです。OSの仮想メモリ、OSやドライバーが管理する情報、クラッシュダンプ、利用者がコピーしたクリップボードは別の管理対象です。
SSDの物理消去やOSによる記録の消去を保証する仕様ではありません。

## 利用者が明示的に作るファイル

訳文のテキスト書き出しと、セッション状態のSQLite書き出しだけを行います。
状態の書き出しには手編集した原文、設定、読書位置、ファイル識別情報が含まれ、翻訳キャッシュは含まれません。
いずれも選択された保存先と同じディレクトリへ一時ファイルを作り、書き込み成功後に置き換えます。
失敗時は一時ファイルを取り除き、既存の書き出し先を保持します。
書き出しの途中でOSからプロセスを強制終了した場合は、明示的な保存先の隣に一時ファイルが残ることがあります。

保存先は、選択中・読込中のPDF/GGUFのパスと、既に開いたファイルの同一性に照らして検査します。
シンボリックリンク、ハードリンク、入力の外部renameにも対応し、置き換え直前に再検査します。
通常の別ファイルへの上書きは従来どおり可能です。

終了操作では、新しい操作の受け付けを停止して、I/Oが受理した書き出しの完了を待ちます。
I/O完了後にだけ、PDF・推論・GUIの終了待ちに対する2秒の期限を開始します。
書き出しが失敗した場合は終了を中止し、内容を保持した画面へ戻して再試行できるようにします。OSからの強制終了や電源断を含めたファイルの耐久性を保証するものではありません。

明示的に書き出した状態ファイルは次回起動時に自動読込しません。
起動ごとにモデルを選び、必要なPDFを開きます。

## メモリの管理

| 対象 | 方針 |
| --- | --- |
| 翻訳キャッシュ | 既定256 MiB。SQLiteの固定schema分を除いたページ割当を含み、使用中文書も同じ上限の対象 |
| 再翻訳の旧試行 | 同じページ・モデル・profileの旧試行と不要な完成本文を置き換える。完成本文の二重保存を廃止 |
| 単一の大きすぎるキャッシュ項目 | 保存しない。GUIにある現在の結果は表示・書き出し可能 |
| 手編集した原文と自動抽出へのリセット | 利用者が作ったセッション状態。キャッシュの削除・ページ移動では破棄しない |
| I/Oの作業キュー | 通常ジョブは64件まで。手編集はページ単位でまとめ、通常キューの満杯で拒否しない |
| GUI layout | 合計32 MiB。単一の巨大layoutも上限の例外にしない |
| layout生成 | 作業・出力を増やす前に予算を確認。既定の作業予算128 MiB、出力予算32 MiB。途中キャンセル可能 |
| PDFium画像キャッシュ | 描画に `FPDF_RENDER_LIMITEDIMAGECACHE` を指定。固定版ではページ単位100 MiB、通常のpage handle保持は最大8ページ。独自タイルキャッシュとは別に制限 |
| UTF-8検証 | 全文の文字配列を作らず走査し、末尾まで検証。準備処理では途中キャンセルを確認 |
| 翻訳のトークン化 | モデルのcontext容量とvocabularyから導ける範囲で事前判定し、巨大な出力配列への再確保を避ける |

これらは各キャッシュ・処理段階の予算であり、アプリ全体のRSS上限ではありません。
モデル本体、PDFiumが解析するページや単一画像のデコード、OS/GUIの割当などは別にメモリを使います。
layoutの作業予算は各コンテナの増加を保守的に計上し、最終layoutの実容量も検査します。
非常に複雑なページで自動抽出を中止した場合も、PDFの表示と必要な原文の手入力を利用できます。

キャッシュから外れた完成訳は再表示時に再生成します。
「完成したページの訳文を書き出す」は、現時点でキャッシュに残り、現在の原文編集と一致する完成訳を対象とします。
長い文書の必要な結果は随時明示的に書き出します。

## 読込中PDFの変更

PDFiumの通常の読み込みは、開いたファイルのハンドルに対する位置指定readを使います。
各readで範囲・ファイル識別情報・サイズ・更新時刻を確認し、Cコールバックを例外が越えないようにします。
POSIXの切り詰め可能なファイルをそのままmmapしてPDFiumへ渡す経路を廃止し、ディスクへのスナップショットも作りません。

Windowsの `FPDF_FILEACCESS` はオフセットが32 bitのため、4 GiB以上のPDFだけは既存の64 bit読込とread-only mappingを使います。
Win32ではmappingが生きている間の切り詰めが禁止されています（[SetEndOfFileの契約](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setendoffile)）。
通常サイズのWindows PDFとmacOS PDFはreadコールバックを使います。
このWindows分岐の実行確認はWindowsで行う必要があります。

## 旧版のファイル

この変更は旧版のファイルを読み込まず、削除もしません。
旧版で編集した原文が必要な場合は、旧版を終了する前に内容を確認・書き出してください。
既存ファイルを新しいアプリが黙って消す移行処理は設けません。

旧版の既定の保存先は次のとおりです。旧版を `--data-dir` で起動していた場合は、その指定先を確認します。

| OS | 旧版の保存先 |
| --- | --- |
| Windows | `%LOCALAPPDATA%\Offline PDF Translator\` |
| macOS | `~/Library/Application Support/Offline PDF Translator/` |

全インスタンスを終了した状態で、旧版が作成した `state.sqlite3`、その `-wal` / `-shm`、`storage.lock`、`Cache/` 内のキャッシュDB、`logs/` を確認します。
`state.sqlite3` には原文編集が含まれ得ます。必要な内容を確保したうえで、不要になったアプリのファイルだけを利用者が削除します。
指定したディレクトリ全体や、同じ場所にあるPDF・GGUF・利用者の書き出し結果を一括削除する手順にはしません。
